Untouched model (existing) Fine-tuned model (proposed), in red as on the drawings

We fine-tuned a 3-billion-parameter vision-language model on seven sheets of one Plan & L-Section drawing set and tested it on a sheet it had never seen. Out of the box the model can read text but misreads which values belong to which bridge and invents details. After about one hour of training it gets the values right on every test question that asks it to read a bridge callout, level block, curve box, benchmark table or title block.

55% → 100% of the values on a bridge callout read correctly (EXG FL, HFL, span, proposal, chainage)
13% → 100% of empty crops correctly answered "no bridge here"; the untouched model invents one 7 times in 8
0% → 38% of named bridges boxed correctly. This is the weak spot, and the fix is in the v2 run

Finding bridges on the sheet

Boxes are precise when it picks the right callout

Asked to box one named bridge, the fine-tuned model got 3 of 8 right, and those three boxes were near exact (overlap 74–98%). The misses have two causes.

  • An ambiguous question on our side. "Where is the callout for bridge 562?" does not say plan or L-section, and one crop can hold both, plus the level block. Three misses boxed the level block instead.
  • Too few examples. Training had only 48 grounding questions. One miss boxed the neighbouring bridge (555 instead of 555A).

The v2 dataset names the view in every question and has 237 grounding examples instead of 48, with everything else left unchanged.

Method

How it was built

  1. Annotations from the PDF itself. The sheets are a vector CAD export, so every callout, level block, curve box and table is real text with coordinates. A script reads them into structured records: 80 bridge records, 77 curve boxes, TBM tables, notes and title blocks. No hand labelling, and every value is exactly what is printed.
  2. Crops and questions. Sheets rendered at 150 dpi (callout text about 20 px tall), cut into 1008 px tiles plus crops around each bridge, curve and table. The records become 1,041 training questions: read this bridge as JSON, explain it, find it, check its levels.
  3. Split by sheet. Sheet 96 for validation, sheet 100 for the test, never trained on. Bridges repeated past a match line are kept out of training too.
  4. LoRA fine-tuning. 41 million adapter weights (1.1% of the model) trained for 2 epochs on one rented L4 GPU, about one hour at $0.50 per hour. The base model stays unchanged.
  5. Scored before and after on the same test questions, with the untouched model as the baseline.
Limits

What this does not show yet

  • One drawing set, one consultant's layout. Other layouts, and General Arrangement Drawings, are untested.
  • Small test. 83 questions, one to eight per task. The v2 run scores all 232 test questions.
  • The "find all bridges" score covers empty crops only, because the random sample drew no crop with a bridge in it. The one full crop checked by hand (above) was right.
  • Explanations follow a learned template. The model reproduces the dataset's phrasing. Values are read from the image, but the wording is not the model's own.
  • No engineering judgement. It reads what is printed. Checks like span against HFL should be done in code on the values it extracts.
Next

Next steps

  1. v2 run, ready to start. Retrain on the fixed grounding data and score the untouched model, v1 and v2 on all 232 test questions in one comparison. About 2 hours on the same GPU, roughly $1.
  2. General Arrangement Drawings. Add GAD sheets to teach bridge components (pier, abutment, pile cap, bearing, wing wall). If they are vector PDFs, the same text-layer method labels them.
  3. A second drawing set from another section or consultant, to test whether the model generalises beyond one layout.
