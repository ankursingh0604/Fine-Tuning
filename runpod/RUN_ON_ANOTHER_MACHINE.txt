RUN THE FINE-TUNED RAILWAY DRAWING MODEL ON ANOTHER MACHINE

What you need
- A computer with an NVIDIA GPU:
    8 GB or more  -> normal (16-bit) mode, best accuracy
    4-8 GB        -> add --4bit (a little less accurate, slower)
  Without an NVIDIA GPU it does not work in practice (CPU is far too slow).
- Python 3.10-3.12, and about 15 GB free disk (the base model is ~7.5 GB, downloaded once).
- Internet the first time (downloads Qwen2.5-VL-3B from Hugging Face).

Files (all in this kit)
- adapter.zip        the trained weights (keep it zipped)
- chat_ui.py         chat page: upload a drawing, ask, compare with the drawing shown beside the chat (+ chat_ui/)
- app.py             older web page with tabs (and the model loader the other tools use)
- ask.py             ask one question from the command line
- read_sheet.py      read a whole sheet image or PDF (uses sheet_reader.py, find_crop.py, band_table.py)
- find_crop.py       finds what a question is about on the sheet, cuts the crop, asks the model
- band_table.py      finds the data band of any L-section (rows, headings, chainages)
- sheet_objects.py   finds the bridges, level crossings, ROBs (callouts, level blocks) and curves on a sheet
- bridge_list.py     the list of all bridges as JSON in the agreed format
- pdf_book.py        all pages of a multi-page PDF asked as one drawing (each question goes to its page)
- sheet_reader.py    the whole-sheet reader: cuts the sheet into pieces the model can read
- sheet_qa.py        answers questions about a sheet from what read_sheet.py read
- layout.py          checks the sheet's layout before reading (see 'Layout check' below)
- test_sheets/       whole-sheet images of test sheets 100, 104, 110 at 150 and 75 dpi
- examples/          crops from test sheet 100 with sample questions
- requirements.txt

Setup (once)
  python -m venv venv
  venv\Scripts\activate            (Windows)    or    source venv/bin/activate   (Linux/Mac)
  pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128
  pip install -r requirements.txt

Quick test from the command line
  python ask.py --adapter adapter.zip --image examples/s100_br560_lsec0.png --question "Read the callout for bridge 560 in this crop and return its details as JSON." --compare

  It should print "adapter attached to ... layers" first. If it says the adapter did not attach,
  upgrade transformers (pip install -U transformers).

Chat page (Railsight: the drawing beside a conversation)
  python chat_ui.py --adapter adapter.zip            then open http://localhost:7860
  (--4bit on small GPUs; --host 0.0.0.0 to open it from other machines on the network: http://<its IP>:7860)
  "+", "Open drawing" or drag and drop opens a PDF (one page or many) or a sheet image, then ask anything printed
  on it. The drawing fills the left (sheet tabs for pages, zoom with the buttons or Ctrl + wheel, drag to pan) so every
  answer can be compared with it; "page 8" in an answer jumps there and the answer's pages are marked on the sheet tabs.
  Below each answer are the crops the model read (click to enlarge); "matches the PDF" in green, CHECK in amber.
  "List all bridges" (or "list all RCC bridges", "list existing bridges" ...) gives a JSON file to download with one
  object per bridge, level crossing, ROB and RUB, in chainage order, exactly these keys (bridge_list.py):
    br_no, chainage (km+m), exg_structure, exg_configuration, description, exs_fl,
    prop_structure, prop_type, prop_configuration, prop_fl, prop_bed_level      (null where the drawing prints nothing)
  The same list also comes as a CSV for Excel (same columns, empty cells for null): "Excel CSV" beside "JSON".
  Every value is the model's reading of the item's callout and level block; values it read differently from the PDF
  are listed in the answer (not in the files). read_sheet.py writes the same two files next to its crops.
  Files: chat_ui.py (the server, FastAPI - installed with gradio) and chat_ui/index.html (the page).

Older web page (tabs)
  python app.py --adapter adapter.zip
  then open http://localhost:7860 in a browser on that machine (other machines on the network: http://<its IP>:7860).
  (add --4bit on small GPUs; add --share for a temporary public link - anyone with the link can use it)
  Tabs:
    Ask about a PDF       upload a drawing PDF (one page or many) and ask anything printed on it - the same questions
                          as read_sheet.py (bridges, curves, grade points, band values, ...). Each answer names its page
                          and shows the crops the model read, with "matches the PDF text" / CHECK for every reading.
    Read a whole sheet    a sheet IMAGE of the trained drawing set: every bridge, levels, band values, CSV.
    Ask about a crop      a crop you cut yourself and a question about it.
  A UI of its own can call app.open_pdf(path, app.model_ask(app.Model(adapter))) once per PDF, then
  app.ask_pdf(book, question) -> (answer text, [(crop image, caption)]) for each question; no gradio needed.

Read a WHOLE sheet image (50-200 dpi)
  Command line:
    python read_sheet.py --adapter adapter.zip --image test_sheets/sheet_100_150dpi.png
  It finds every bridge callout, reads each callout and level block, reads the two printed data-band
  columns either side of the bridge chainage and interpolates every band value between them,
  y = y1 + (y2 - y1) / (x2 - x1) * (x - x1) (on a printed column, y is that column), then the title block
  and TBM table. Answers always give y and show x1, x2, y1, y2. It writes a folder
  sheet_100_150dpi_read/ with:
    ..._bridges.csv   one row per bridge (opens in Excel)
    ..._read.json     everything read
    ..._overlay.png   the sheet with the bridges found boxed (red = FLAG/CHECK)
  FL below MIN FL is reported as "FLAG: For bridge X min. FL = .., and FL = ..".
  About 120 questions to the model per sheet (two band columns per bridge): roughly 6-12 minutes on an RTX 3060.
  Readings saved by the earlier version still answer, marked as nearest-column values; add --reread to interpolate.

  Ask questions about the sheet (the reading above is saved and reused, so answers come instantly):
    python read_sheet.py --adapter adapter.zip --image test_sheets/sheet_100_150dpi.png -q "ground level at bridge 560"
    python read_sheet.py --adapter adapter.zip --image test_sheets/sheet_100_150dpi.png -q "bridge 560" -q "which bridges are flagged"
    python read_sheet.py --adapter adapter.zip --image test_sheets/sheet_100_150dpi.png -i     (keeps asking at a prompt)
  Examples of questions:
    bridge 560 (full report)      ground level at bridge 560     FL of 558      min FL of 562     levels of 565
    HFL at 565    free board at 532    cut or fill at 560    rail level and track distance at 560
    span of 554   proposal for 560     ROB-239    LC-226     ground level at CH 1241000     1242+662.9
    which bridges are flagged     list bridges     summary     drawing number     scale     TBM BM39     help
  A chainage away from any bridge makes the model read that band column (a few seconds), which is why
  --adapter stays on the command line. Add --reread to read the sheet again from scratch.
  Web page: the "Read a whole sheet" tab of app.py does the same, with a CSV download.
  test_sheets/ has sheets 100, 104, 110 (never seen in training) at 150 and 75 dpi.
  Below ~100 dpi the text is under 13 px tall, so expect misread digits; 150-200 dpi is best.
  Layout check: before reading, layout.py checks the sheet's layout from the image (table rules, band row
  labels read with a local OCR, column spacing, title block / TBM headings) and prints
  "Layout: known / similar / unknown (confidence high / medium / low)".
    known    - this drawing set's layout: read exactly as trained
    similar  - same rows but moved / re-ordered / different spacing: read from the detected positions, check values
    unknown  - rows missing or not recognised: those parts are skipped and the reasons listed, nothing is guessed
  Band values that do not add up (FL - GL = cut/fill, RL - FL = 0.762, FL difference) also lower the confidence.
  The OCR (rapidocr_onnxruntime) is in requirements.txt; without it the row labels are not checked.

PDFs, gradients and anything else printed on the sheet (find_crop.py)
  A PDF can be given directly (it is rendered so its text is as tall as on the trained sheets, whatever the page size):
    python read_sheet.py --adapter adapter.zip --image sheet.pdf --find-only -i
  --find-only skips the whole-sheet reading (bridges and bands, several minutes) when you only want questions like these.
  A PDF with several pages, given WITHOUT --page, is asked as one drawing (pdf_book.py): every page's text is indexed
    first (a few seconds for 17 pages - bridges, curves, the chainages each page's band covers), then each question goes
    to the page(s) that print what it asks about, and only those pages are rendered and read by the model. Every answer
    says its page ("[page 8]"). A list of bridges covers every page; a bridge printed again at the start of the next
    sheet is listed once ("[pages 2, 3]"); a chainage on the border of two sheets is answered from both.
      python read_sheet.py --adapter adapter.zip --image "MKN_PNP_1040-1068_3rd Line(From Indergarh).pdf" -i
  --page 2 opens just that page (and allows the whole-sheet reading, as for a one-page PDF).
  Gradient / grade-point questions:   gradient at CH 10046    slope at 9390    gradient at 1241+713
    The grade-point symbol is found (chainage label, FL, the gradient label on each side of the stem); every other text
    around it is blanked, and each label is read by the model in its own small crop, so a neighbouring symbol's FL is
    never taken. No FL printed -> "FL: not printed for this grade point". For a PDF each reading is compared with the
    PDF's own text: "matches the PDF text" or "CHECK: the PDF text says ...".
  Data-band values on ANY L-section PDF (band_table.py): the band table is found from the sheet's own layout - each
    row named by the heading printed left of it, the chainage of every column from the chainage row - so it works for
    any drawing set, not only the trained one.
      cut/fill at C-8 TPCC2      ground level at BR NO. 15      FL at 11540      OGL at 11000
      proposed FL UP main 2 at 11384      track distance at 1246000      cut or fill at 1245+300
    The chainage comes from the question, or from the label it names ("C-8. TPCC2 AT Ch. 11701.654m."). The model reads
    the printed column there, or the two columns either side (each from its own crop, neighbours and table lines
    blanked), and the value is interpolated: x1, x2, y1, y2 are shown, each reading compared with the PDF text. Several
    rows fitting the question (FL of DN Main 2 and of UP Main 2) are all answered. A row the sheet does not have, or a
    chainage off the sheet, is said so - nothing is guessed.
    Where the gradient changes between two printed columns (a grade point), the value is taken along the stretch that
    holds the chainage, from the grade point (FL printed there) - not straight from column to column.
  Bridges and curves (sheet_objects.py), on any drawing set's callouts ("PROP. Br. No. :15, SPAN : 1 X 3.66M. ...",
    "C/L OF EXG. BR. NO. 575 DN RCC SLAB - ... AT CH: 1245630.853"):
      list all bridges      list all RCC bridges      list existing hume pipe bridges
      chainage of existing Br. No. 16      span of Br. No. 17      FL of PROP Br. No. 17      HFL of Br. No. 15
      which curve is near Br. No. 15      curve near CH 12000      details of curve 8
    Every callout is read by the model from a crop of its own lines only (a label that wraps onto the next line is
    joined; diagonal labels are turned to read left to right); the answer is taken from that reading and compared with
    the PDF text. EX / existing and PROP / proposed are told apart.
  Any other question the fixed list does not cover (e.g. "span of BR NO. 12", "speed on curve C.NO.-1"): the text is
    found on the sheet, a crop around it is shown to the model with your question. A number that is printed nowhere on
    the sheet gives "not printed anywhere on this sheet" - nothing is guessed.
  The crops used are saved in <out folder>/crops/ so you can look at what the model saw.
  For images (not PDFs) the text is located with the local OCR, once per sheet (a few minutes on a CPU, then cached).

Expected answer for the quick test (bridge 560, sheet 100):
  {"bridge_id": "560", "existing_type": "ARCH", "existing_span": "1 X 0.61", "crossing": "DRAIN",
   "proposal": "1 X 2 X 2 - RCC BOX", "category": "MINOR", "chainage_m": 1242662.9, "levels": {...}}

Things to remember
- Numbers from the model can contain small misreads (a digit or a sign). Check important values.
- Crops work best like the training ones: rendered from the PDF at about 150 dpi, text clearly readable.
